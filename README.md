# Агент-сметчик — ДЗ Шаг 1 (tool-calling) и Шаг 2 (RAG)

Агент считает смету по брифу клиента и поднимает из архива похожие прошлые
проекты. Шаг 1 — цикл tool-calling без фреймворков. Шаг 2 — RAG, подключённый
к тому же агенту пятым инструментом, а не отдельным скриптом.

**Подробный отчёт по обоим шагам: [REPORT.md](REPORT.md)**

Структура:

```
agent_openrouter.py   рабочий агент (OpenRouter)
agent_anthropic.py    тот же цикл на Anthropic SDK, ждёт ключа
common.py             общая часть обеих реализаций
tools.py              5 инструментов + JSON-схемы
rag/                  RAG руками: чанкинг, эмбеддинги, Qdrant, поиск
rag_llamaindex.py     то же на LlamaIndex (часть Б Шага 2)
check_key.py          остаток суточного лимита без расхода квоты
data/knowledge/       корпус: 25 карточек проектов + методика оценки
logs/                 логи прогонов
```

Две реализации одного и того же цикла:

- **`agent_openrouter.py`** — рабочая, через OpenRouter (OpenAI-совместимый API);
- **`agent_anthropic.py`** — на официальном Anthropic SDK, ждёт ключа.

Общая часть (системный промпт, сценарии, логирование, выполнение инструментов)
вынесена в `common.py`, поэтому **разница между двумя файлами — это ровно то,
чем отличаются провайдеры, и ничего больше.** Открыть рядом и сравнить —
самый быстрый способ понять, что цикл агента от провайдера не зависит.

## Записка об отрасли (контекст для преподавателя)

Я фрилансер-веб-разработчик: сайты, интернет-магазины, веб-приложения, CRM,
админ-панели, парсеры. Работаю методом вайб-кодинга, поэтому техническая часть
перестала быть узким местом — узким местом стал **пресейл**.

Специфика, из которой вырос этот агент:

- **Оценка проекта — не программирование, а рутина.** На входе бриф в свободной
  форме. На выходе смета: базовая цена типа проекта плюс доплаты за модули,
  сверка с бюджетом клиента, разбивка на платежи. На один бриф уходит от
  40 минут.
- **Большая часть брифов не конвертируется.** Заявок много, оплаченных проектов
  мало, а считать приходится каждую. Чистые невозвратные издержки.
- **С распространением нейросетевых инструментов конкурентов стало объективно
  больше.** Отстроиться самой разработкой трудно, а скоростью ответа на заявку —
  можно. Смета за минуту вместо «пришлю к концу недели» — это преимущество.
- **Цены — коммерческая информация и часто меняются.** Поэтому они лежат в
  локальном `data/pricelist.json`, а не в промпте: модель не должна их знать и
  тем более придумывать. Отсюда прямое требование к агенту: любую цену берёт
  только инструментом, любой расчёт делает только калькулятором.

Дальняя цель — довести до продукта: агент принимает заявку, ищет похожие прошлые
проекты и выдаёт смету с коммерческим предложением.

> Цены в `data/pricelist.json` сейчас **ориентировочные рыночные**, не мои
> реальные. Структура (база за тип проекта + доплаты за модули) — настоящая.

## Инструменты

| Инструмент | Что делает | Зачем в задании |
|---|---|---|
| `read_brief(filename)` | читает текстовый файл из `data/`, только оттуда | чтение локального файла |
| `get_price(item)` | цена одной позиции из прайса: база или доплата | справочник; одна позиция за вызов — так получается цепочка |
| `calculate(expression)` | арифметика через `ast`, **без `eval`** | безопасный калькулятор |
| `search_projects(query)` | векторный поиск по архиву прошлых проектов | Шаг 2: RAG как инструмент агента |
| `get_weather(city)` | заглушка с погодой | приманка: проверяет, что агент **выбирает** инструменты, а не вызывает все подряд |

## Как это работает

```
вопрос -> [ модель + список инструментов ]
              |
              +-- инструменты не нужны    -> финальный текст, выход
              |
              +-- модель просит инструмент -> выполнить функцию
                        |
                        +-- ок      -> результат
                        +-- ошибка  -> текст ошибки с пометкой
                                            |
                                            v
                              всё дописывается в messages, новый оборот цикла
```

Тот же цикл как BPMN-схема:
https://stormbpmn.com/app/diagram/850cd755-12be-4b75-9a4a-4e429033c8b6

Важное: модель никогда не выполняет код. Она возвращает имя инструмента и
аргументы, выполняет их агент. API при этом stateless — на каждом обороте вся
история отправляется заново, и в логе видно, как растёт число входных токенов.

## Чем различаются провайдеры

Цикл одинаковый, различается упаковка:

| | Anthropic | OpenRouter / OpenAI |
|---|---|---|
| признак «нужен инструмент» | `stop_reason == "tool_use"` | `finish_reason == "tool_calls"` |
| где лежит запрос | блок внутри `content` | отдельное поле `tool_calls` |
| аргументы | готовый словарь | **строка JSON**, нужен `json.loads` |
| ключ схемы | `input_schema` | `parameters` внутри `{"type":"function"}` |
| результат инструмента | блок `tool_result` в сообщении `user` | отдельное сообщение с ролью `tool` |
| системный промпт | отдельный параметр `system` | первое сообщение в `messages` |
| пометка ошибки | поле `is_error` | **поля нет**, ошибка передаётся текстом |

## Обработка ошибок

Выполнение инструмента (`run_tool` в `common.py`) не даёт процессу упасть никогда:

- `ToolError` — предсказуемая ошибка: нет файла, нет позиции в прайсе, деление на ноль;
- `TypeError` — модель передала не тот набор аргументов;
- любое другое исключение — ловится как непредвиденное;
- **только у OpenAI-формата:** модель присылает битый JSON в аргументах —
  `JSONDecodeError` тоже превращается в ошибку инструмента.

Во всех случаях текст ошибки уходит модели как результат вызова, и она получает
шанс исправиться на следующем витке. Сообщения об ошибках намеренно подсказывают
выход: `get_price` перечисляет все доступные позиции прайса.

## Запуск

```bash
python -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt
copy .env.example .env      # и вписать свой ключ OpenRouter

python check_key.py                  # ключ живой? сколько запросов осталось?
python agent_openrouter.py --test 1  # главный сценарий
```

Сценарии:

1. **Многошаговый**: прочитать бриф -> узнать цену по каждой позиции отдельно ->
   сложить -> сверить с бюджетом -> посчитать платёж при рассрочке.
2. **Выбор инструментов**: «15% от 340, а потом тепло ли в Амстердаме» — пример
   из задания.
3. **Ошибки**: несуществующая позиция прайса и деление на ноль — агент получает
   ошибки, не падает и всё равно доводит задачу до конца.

4. **Шаг 1 + Шаг 2**: найти в архиве похожие проекты, назвать риски и посчитать
   цену по прайсу — агент сам комбинирует RAG и прайс-лист.

Свой вопрос: `python agent_openrouter.py "Посчитай смету по brief_shop.txt"`.

## Шаг 2: RAG

```bash
python -m rag.chunking       # как режутся чанки (без обращений к API)
python -m rag.embeddings     # проверка, что эмбеддинги измеряют смысл (1 запрос)
python -m rag.index          # индексация корпуса в Qdrant (2 запроса)
python -m rag.search --test  # проверка пункта 2.7 (4 запроса)
python rag_llamaindex.py --test   # то же на LlamaIndex
```

Qdrant работает в **local mode** без Docker: `QdrantClient(path="./qdrant_data")`.
Это официальная фича клиента, тот же API; для серверного Qdrant меняется одна
строка подключения. Подробности и сравнение с LlamaIndex — в [REPORT.md](REPORT.md).

## Ограничение бесплатного тарифа

OpenRouter на бесплатных моделях: **20 запросов в минуту, 50 в сутки**.
Один запрос — это один оборот цикла, а не один вопрос. Главный сценарий стоит
~12 запросов, все три вместе ~21. То есть **два полных прогона в сутки**.

Поэтому сценарии запускаются по одному (`--test 1`), повторы в SDK отключены
(`max_retries=0`), лимит шагов снижен до 8, а `check_key.py` показывает остаток
до того, как начинать.
