# Отчёт по ДЗ: Шаг 1 (tool-calling) и Шаг 2 (RAG)

Репозиторий: https://github.com/sergevipcoder-beep/estimator-agent

Один проект на оба шага: агент-сметчик, который считает смету по брифу клиента
и поднимает из архива похожие прошлые проекты. Шаг 2 не отдельный скрипт —
RAG подключён к агенту из Шага 1 пятым инструментом.

## Чем запускалось

Ключей Anthropic у курса не было, поэтому рабочий провайдер — **OpenRouter**
(задание допускает «или аналог»). Anthropic-версия написана и лежит рядом,
заработает без правок, когда появится ключ.

- модель ответов: `nvidia/nemotron-3-super-120b-a12b:free`
- модель эмбеддингов: `nvidia/nemotron-3-embed-1b:free`, размерность 2048
- Python 3.14.4, Windows
- бесплатный тариф: 20 запросов в минуту, 50 в сутки

# Шаг 1. Raw tool-calling

## Критерии готовности

| Критерий | Статус | Где смотреть |
|---|---|---|
| агент отвечает на вопросы, требующие вызова инструментов | выполнено | `logs/*-test1.md`, `logs/*-test4.md` |
| есть обработка ошибок инструмента | выполнено | `logs/*-test3.md` |
| ни одной сторонней agent-библиотеки | выполнено | только SDK провайдера + `while` |
| ключ в `.env`, не в git | выполнено | `.gitignore`, `git log --stat` |

## Инструменты

| Инструмент | Что делает |
|---|---|
| `read_brief(filename)` | читает файл из `data/`, только оттуда |
| `get_price(item)` | цена позиции из прайса: база за тип проекта или доплата за модуль |
| `calculate(expression)` | арифметика через `ast`, без `eval` |
| `search_projects(query)` | **RAG по архиву прошлых проектов (Шаг 2)** |
| `get_weather(city)` | заглушка-приманка: проверяет, что агент выбирает инструменты |

## Две реализации одного цикла

`agent_openrouter.py` и `agent_anthropic.py`. Общая часть (промпт, сценарии,
логирование, выполнение инструментов) вынесена в `common.py`, поэтому разница
между файлами — ровно то, чем отличаются провайдеры:

| | Anthropic | OpenRouter / OpenAI |
|---|---|---|
| признак «нужен инструмент» | `stop_reason == "tool_use"` | `finish_reason == "tool_calls"` |
| где запрос | блок внутри `content` | отдельное поле `tool_calls` |
| аргументы | готовый словарь | **строка JSON**, нужен `json.loads` |
| ключ схемы | `input_schema` | `parameters` внутри `{"type":"function"}` |
| результат инструмента | блок `tool_result` в сообщении `user` | отдельное сообщение с ролью `tool` |
| системный промпт | отдельный параметр `system` | первое сообщение в `messages` |
| пометка ошибки | поле `is_error` | **поля нет** |

**Честное расхождение с пунктом 1.4.** Задание требует вернуть ошибку
«как `tool_result` с пометкой ошибки». В OpenAI-совместимом API поля `is_error`
не существует — ошибка передаётся текстом с префиксом `ОШИБКА:`. В
Anthropic-версии используется настоящее поле `is_error`. Требование выполнено
по смыслу, но в OpenRouter-версии не дословно, и это ограничение API, а не кода.

## Обработка ошибок: четыре класса

1. `ToolError` — предсказуемое: нет файла, нет позиции в прайсе, деление на ноль.
2. `TypeError` — модель передала не тот набор аргументов.
3. Любое другое исключение — как непредвиденное, процесс не падает.
4. **Только в OpenAI-формате:** битый JSON в аргументах — `JSONDecodeError`.
   У Anthropic такого класса ошибок не бывает, потому что аргументы приходят
   готовым словарём.

Плюс обработка сбоев самого провайдера: 429 (лимит), 402 (кредиты) и пустой
ответ без `choices`.

## Что показали логи

**`logs/20260930-162355-test3.md` — обработка ошибок.** Агент запросил
несуществующую позицию «котик», получил ошибку со списком доступных позиций,
затем попробовал посчитать `10 / 0`, получил «деление на ноль» — и всё равно
довёл задачу до финального ответа, корректно описав обе ошибки.

**`logs/20260930-163928-test1.md` — находка, которой не было бы при гладком
прогоне.** Модель **пять раз подряд** не смогла угадать позицию «платёжный
шлюз»: пробовала «платежный шлюз» (без «ё»), `payment gateway`, с заглавной
буквы, через дефис. Правильное написание сообщалось ей в тексте каждой ошибки.

Это показало реальную проблему конструкции: инструмент искал точным совпадением
строки. Исправлено в `get_price` — нормализация «ё/е» и поиск по подстроке и по
описанию позиции. Вывод шире самого бага: **инструмент должен быть терпим к
неточным аргументам, иначе агент тратит обороты цикла на угадывание написания.**

В том же логе провайдер вернул ответ вообще без `choices` — добавлена обработка
(один повтор шага, при двух подряд остановка).

**`logs/20260930-162611-test2.md` — пример из задания** про «15% от 340 и погоду
в Амстердаме». Агент вызвал `get_weather` с `Amsterdam`, получил ошибку со
списком известных городов и сам исправился на кириллицу. Погоду при расчёте
сметы не вызывал ни разу — то есть инструменты действительно выбираются, а не
перебираются.

# Шаг 2. RAG

## Критерии готовности

| Критерий | Статус | Где смотреть |
|---|---|---|
| рабочий RAG на своём коде, без LlamaIndex | выполнено | `rag/` |
| тот же агент на LlamaIndex | выполнено | `rag_llamaindex.py` |
| сравнение двух вариантов | ниже в этом файле | |
| не выдумывает, когда ответа нет | выполнено | `logs/rag-test-2.7.md` |

## Корпус

`data/knowledge/` — 26 документов: 25 коротких карточек проектов (тип, итоговая
цена, срок, что пошло не так, вывод) и один длинный документ «Методика оценки
проектов» со сводными правилами.

Карточки — **демо-данные**, не реальный архив. Структура соответствует тому,
как эта база выглядела бы в работе.

## Что сделано руками (`rag/`)

| Файл | Что делает |
|---|---|
| `rag/chunking.py` | режет документы на чанки с перехлёстом |
| `rag/embeddings.py` | эмбеддинги через OpenRouter, батчами |
| `rag/index.py` | Qdrant local mode, загрузка с метаданными |
| `rag/search.py` | поиск top-5 + генерация строго по контексту |

### Qdrant без Docker

Задание предлагает `docker run -p 6333:6333 qdrant/qdrant`. Docker на машине не
установлен, и он не понадобился: у `qdrant-client` есть официальный **local
mode**:

```python
QdrantClient(path="./qdrant_data")   # вместо QdrantClient(url="http://localhost:6333")
```

Это тот же самый клиент и тот же API («Everything Qdrant server can do, but
locally» — из исходников `QdrantLocal`). Чтобы переехать на серверный Qdrant,
меняется ровно одна строка подключения. Версия 1.19.1 заявляет поддержку
Python 3.14.

### Нюанс, которого нет в задании: токены кириллицы

Задание просит чанки по 300-500 токенов. Токенизатор режет русский текст
гораздо мельче латиницы: для кириллицы один токен — это примерно **2-3
символа**, для английского около 4. Значит 400 токенов по-русски — это около
**1000 символов**, а не 1600. Если взять английскую пропорцию, чанки вылезут
за заданный диапазон почти вдвое.

Итог на нашем корпусе: `target_chars=1000`, `overlap_chars=150` →
36 чанков, оценка 224-396 токенов, в среднем 290.

Короткие карточки целиком укладываются в один чанк — это нормальный результат,
а не недоработка: резать документ на 670 символов было бы искусственно.
Перехлёст реально задействуется на длинном документе «Методика оценки»,
который разрезан на 11 чанков.

### Эмбеддинги: батчи вместо запроса на чанк

Поле `input` принимает список текстов, поэтому весь корпус из 36 чанков
индексируется за **2 запроса** вместо 36. При лимите 50 запросов в сутки это
решающая деталь.

Размерность вектора в каталоге OpenRouter не указана — получаем её из первого
ответа (`len(embedding)` = 2048), потому что Qdrant требует размер вектора
при создании коллекции.

### Проверка, что эмбеддинги измеряют смысл, а не слова

`python -m rag.embeddings` (1 запрос):

```
0.798  интернет-магазин автозапчастей  <->  магазин по продаже деталей для автомобилей
0.103  интернет-магазин автозапчастей  <->  рецепт борща со сметаной
0.082  магазин по продаже деталей для автомобилей  <->  рецепт борща со сметаной
```

Первые две фразы почти не имеют общих слов, но близки по смыслу. Это прямо
отвечает на проблему из Шага 1: строковый поиск споткнулся на букве «ё»,
векторный такой проблемы не имеет по своей природе.

## Проверка пункта 2.7 — `logs/rag-test-2.7.md`

**Вопрос, ответ на который есть в корпусе:** «Из-за чего сорвали срок в проекте
с интеграцией 1С и на сколько?»

Найдено с близостью 0.614 (`01-magazin-avtozapchasti.md`) и 0.573
(`00-metodika-ocenki.md`). Ответ точный: самописная доработка 1С, дубли
номенклатуры, слой сопоставления артикулов, 90 часов вместо 40, срыв на
2 месяца. Источники названы.

**Вопрос, ответа на который нет:** «Делали ли мы мобильное приложение на Flutter
для доставки еды и сколько оно стоило?»

Ответ: «В архиве проектов нет информации по этому вопросу.» Ни одной выдуманной
цифры.

Отдельно показательна близость найденного: на вопросе с ответом максимум
**0.614**, на вопросе без ответа — **0.336**. То есть поиск всегда возвращает
top-5, даже когда в корпусе ничего подходящего нет, и защитой от выдумывания
служит не поиск, а формулировка промпта:

> Если в контексте нет ответа, напиши ровно: «В архиве проектов нет информации
> по этому вопросу.» и не добавляй никаких догадок из общих знаний.

Это главный практический вывод Шага 2: **галлюцинации в RAG лечатся промптом,
а не кодом поиска.** Разницу в близости (0.61 против 0.34) можно было бы
использовать как порог отсечения, но тогда отсечение станет жёстким правилом,
а задание требует, чтобы решение принимала модель.

## Сшивка с Шагом 1 — `logs/20261004-184507-test4.md`

RAG подключён к агенту инструментом `search_projects`. Вопрос:

> «Клиент хочет интернет-магазин автозапчастей с интеграцией 1С. Найди в архиве

> оценке, и посчитай цену по прайсу.»

Агент за 5 оборотов цикла сам выстроил цепочку: `search_projects` → `get_price`
(интернет-магазин) → `get_price` (интеграция с 1С) → `calculate` → ответ.
В финале — таблица похожих проектов с фактами из архива, список рисков,
ошибка в оценке (40 часов плана против 90 факта), смета 850 000 и рекомендация
запросить тестовую выгрузку 1С до начала работ.

Это и есть смысл обоих шагов вместе: без RAG агент умел считать по прайсу, а с
RAG начал опираться на прошлый опыт.

## Часть Б: то же на LlamaIndex (`rag_llamaindex.py`)

| Что делаем | Руками (`rag/`) | LlamaIndex |
|---|---|---|
| чтение файлов | glob + `read_text` | `SimpleDirectoryReader` |
| резка на чанки | `split_text()` с перехлёстом | `SentenceSplitter` |
| эмбеддинги батчами | `rag/embeddings.py` | `OpenAILikeEmbedding` |
| векторное хранилище | `rag/index.py` + Qdrant | `VectorStoreIndex` |
| поиск + сборка промпта | `rag/search.py` | `as_query_engine()` |
| объём кода | ~200 строк в 4 файлах | ~20 строк логики |

Результат на тех же двух вопросах — идентичный: точный ответ с теми же фактами
и честный отказ на вопрос вне корпуса (`logs/rag-llamaindex-test.md`).

### Что LlamaIndex сделал за нас

Чанкинг, вызов эмбеддингов батчами, хранение векторов, подстановку найденного
в шаблон промпта и сборку ответа. Индексация корпуса — буквально две строки:

```python
documents = SimpleDirectoryReader(str(KNOWLEDGE_DIR)).load_data()
index = VectorStoreIndex.from_documents(documents)
```

### Где это помешает при тонкой настройке

1. **Чанкинг считается в токенах, а не символах.** На нашем корпусе LlamaIndex
   дал 38 узлов против наших 36 при номинально тех же настройках. Чтобы
   получить ровно нужную нарезку для кириллицы, надо разбираться во внутренностях
   `SentenceSplitter`, тогда как в своём коде это один параметр.
2. **Промпт спрятан.** Наш анти-галлюцинационный промпт пришлось передавать
   через `system_prompt` у LLM, потому что шаблон синтеза ответа лежит внутри
   библиотеки. В своём коде промпт — это просто строка на виду.
3. **Неочевидно, сколько запросов уходит в API.** `compact_and_refine` может
   сделать несколько обращений к модели на один вопрос. При лимите 50 запросов
   в сутки это существенно, а в своём коде всегда ровно два запроса на вопрос.
4. **Зависимости.** См. ниже.

### Две реальные проблемы, которых не было в своей версии

**1. `llama-index-vector-stores-qdrant` не ставится на Python 3.14.**
У пакета `requires_python = ">=3.10,<3.14"`. При попытке установки pip
откатывается на старые версии зависимостей, доходит до numpy без готовых
сборок под 3.14, пытается собрать его из исходников и падает на отсутствии
компилятора C. Поэтому в LlamaIndex-версии используется встроенное хранилище
вместо Qdrant. На механику RAG это не влияет — меняется только место хранения
векторов.

**2. Конфликт версий `httpx` и SSL.** LlamaIndex тянет классический `httpx`
со вшитым списком корневых сертификатов, тогда как свежий `openai` использует
`httpx2`. На машине с собственным сертификатом в цепочке (антивирус или
корпоративный прокси) получилось так: наши прямые вызовы и индексация работали,
а генерация через LlamaIndex падала с `CERTIFICATE_VERIFY_FAILED`. Решено
пакетом `truststore` — Python берёт сертификаты из хранилища ОС. Проверку
сертификатов не отключали.

Это и есть практический ответ на вопрос «что упрощает фреймворк, а где мешает»:
двадцать строк вместо двухсот, но взамен — чужое дерево зависимостей и
диагностика ошибок на три уровня глубже.

# Наблюдения

1. **Агент — это цикл, а не модель.** Модель возвращает имя инструмента и
   аргументы, выполняет функции мой код. Убрать обратную дугу из цикла —
   получится обычный чат-бот.
2. **API stateless, и это видно в логах.** Входные токены растут 1061 → 4074 за
   прогон, потому что вся история отправляется заново каждый оборот. Отсюда и
   цена, и переполнение контекста, и необходимость RAG.
3. **Стоимость считается в оборотах цикла, а не в вопросах.** Один вопрос
   «посчитай смету» — это 12-15 запросов к API. Чем самостоятельнее агент, тем
   больше оборотов.
4. **`description` в схеме инструмента — это промпт, а не документация.**
   От формулировки зависит, вызовет модель инструмент или нет.
5. **Инструмент должен быть терпим к неточным аргументам.** Пять потраченных
   оборотов на угадывание «платёжный шлюз» — прямая плата за строгий поиск
   по строке.
6. **Ошибка инструмента делает агента умнее.** Если в текст ошибки положить
   список доступных вариантов, модель исправляется сама.
7. **Галлюцинации RAG лечатся промптом.** Поиск всегда вернёт top-5, даже когда
   в корпусе ответа нет. Решает формулировка «если в контексте нет ответа —
   скажи, что нет».
8. **Кириллица стоит вдвое дороже в токенах.** Влияет и на размер чанка, и на
   цену запроса.
9. **Свежий Python — отдельный источник проблем.** На 3.14 не поставилась
   Qdrant-интеграция LlamaIndex, `httpx` переименовался в `httpx2`, а кириллица
   в `print` падает без `sys.stdout.reconfigure`.
10. **У агента-ревьюера своя целевая функция.** Встроенный мастер StormBPMN
    отревьюил BPMN-схему цикла и выдал шесть замечаний, из которых по делу было
    одно (не обрабатывались ошибки самого вызова модели — и это действительно
    вылезло позже пустым ответом провайдера). Остальное — правила линтера,
    применённые механически, потому что его задача — поднять оценку качества
    диаграммы, а не помочь сдать ДЗ.

# Шпаргалка: что говорю на созвоне

- **Агент** = модель + цикл + инструменты. Модель только *просит* вызвать
  функцию, выполняет мой код. Сколько будет шагов — заранее неизвестно, порядок
  выбирает модель, поэтому в коде `while`, а не последовательность.
- **Ошибка инструмента** возвращается модели как результат с пометкой, и она
  исправляется сама. Поэтому агент не падает.
- **RAG** нужен, потому что вся база в промпт не влезет: ищем по смыслу
  5 ближайших кусков и подкладываем только их. Эмбеддинг — это текст, переведённый
  в числа так, что близкое по смыслу оказывается рядом.
- **Честность RAG** — это не поиск, а промпт: поиск всегда что-то вернёт,
  отказываться от ответа модель должна по инструкции.
- **Фреймворк** экономит 180 строк из 200, но забирает контроль над чанкингом,
  промптом и числом запросов — и приносит своё дерево зависимостей.
